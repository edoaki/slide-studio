# Electron・JS／TS移行と配布の実装計画

作成日：2026-11-12。状態：実装前。対象：`edoaki/slide-studio` と紹介サイト `slide-studio-web`。

## 1. 目標と確定方針

Git・ターミナル・Python・uvに慣れていない利用者が、アプリをダウンロードして開き、保存フォルダを選ぶだけで編集・書き出しを始められるようにする。

- デスクトップ版はElectron、アプリ処理はTypeScriptを中心としたJS／TSへ移す。Tauri・Rustは採用しない。
- ブラウザー版とデスクトップ版を、同じアプリリポジトリ・共通処理・保存形式・バージョンで管理する。
- 一般利用者向けの最終配布物には、Python・uv・別途ダウンロードするPlaywright用Chromiumを必要としない。
- Electron同梱Chromiumを表示・検査・画像生成・PDF出力に使う。PandocはOS・CPU別の実行ファイルを同梱する。
- 利用者が指定した保管フォルダに原稿・資料・テーマ・履歴を保存する。アプリの更新とデータを分離する。
- アプリの配布物は`edoaki/slide-studio`のGitHub Releasesへ置き、`slide-studio-web`からリンクする。
- ソースを改造する人向けに、開発用のブラウザー起動・デスクトップ起動・ビルド手順を用意する。
- 実装担当はOpenCode経由のDeepSeekを並列利用する。相談・行き詰まりの調査・レビューにはClaude Code CLIのOpus 5.5、effort highを使う。

「GitHubを1つ」はアプリのブラウザー版とデスクトップ版を分割しない意味とする。既存の紹介サイトリポジトリは維持し、アプリのコードや配布バイナリを複製しない。

この文書は実装計画であり、現時点で移植・公開・リリースが完了したことを示さない。

## 2. 現状と移植対象

現在はPythonのHTTPサーバーが画面を配信し、Macでは主にChromeの専用ウィンドウ、その他では既定ブラウザーを開く。検査・画像生成・PDF出力は、PythonのPlaywrightから別のChromiumを操作している。

| 領域 | 現在の入口 | 移植後の担当 |
|---|---|---|
| 保存場所・初回選択・CLI | `workspace.py`、`location.py`、`cli.py` | core/workspace、server、CLI、Electronのフォルダ選択 |
| 原稿解析・部分編集 | `source.py`、`edit.py`、`edit_scope.py` | core/source、core/edit |
| HTML生成・Pandoc常駐 | `render.py`、`pandoc_worker.py`、`lua/` | core/render、platform/pandoc。Luaは原則継続 |
| HTML書き出し・検査・PDF | `bundle.py`、`check.py`、`export.py`、`shots.py`、`theme_shots.py` | core/export、rendererサービス |
| HTTP・SSE・監視・終了 | `server.py`、`background_check.py`、`lifeline.py` | server、job管理、Electron lifecycle |
| 発表・資料・文献・テーマ | `deck_manage.py`、`materials.py`、`bibliography.py`、`themes.py`等 | coreの各サービス |
| 履歴・復元・移行 | `history.py`、`snapshot.py`、`topic_migrate.py`等 | core/history、core/migrations |
| AI通信・権限・ログイン | `ai/` | ai/providers、process管理、CLI bridge |
| アプリなしの再ビルド | `portable.py`、`templates/portable/build.py` | 独立配布のコンパイラーと移行案内 |
| 編集画面・配布HTML | `web/`、`runtime/`、`templates/` | 共通Web資産。原則として既存の素のJSを維持 |

この表だけを機能一覧としない。M0でREADME・ルート・CLI・既存テストから機能対応表を作り、未移植・代替・検証済みを記録する。原稿、メモ、直接編集、素材・文献、テーマ、AIの各役割、履歴、HTML／PDF、可搬フォルダの機能を無断で落とさない。

## 3. リポジトリと開発環境

### 3.1 ローカル作業ディレクトリ

実装開始時に、現行の`/Users/aki/code/slide-studio`を`/Users/aki/code/slide-studio-old`へ移し、Electron移行用のworktreeを`/Users/aki/code/slide-studio`に作る。移行用ブランチは`migration/electron`とする。

```text
/Users/aki/code/
  slide-studio-old/          現行Python版。動作比較・通常利用用
  slide-studio/              Electron移行版。migration/electronのworktree
  slide-studio-web/          既存の紹介サイト
```

両アプリディレクトリは同じGitリポジトリ・origin・履歴を共有する。公開先は引き続き`edoaki/slide-studio`で、ローカルのディレクトリ名を理由にGitHubリポジトリ名を変更しない。完成後は新しい`slide-studio`側で移行ブランチをmainへ統合し、mainで開発を続ける。その前に、mainを開いている別worktreeがあれば状態を確認して切り替え、旧版の`legacy/python`には移行変更をマージしない。

M0の最初に次の順で配置を整える。

1. 起動中のアプリ・監視処理・実装エージェントを止め、Gitの状態、既存worktree、移動先の有無を確認する。既存ディレクトリを上書きしない。
2. 比較基準となるコミットを記録する。本計画など移行版に必要な変更は内容を選別してコミットし、未コミット・未追跡の利用者の変更は保持する。worktree作成だけでは未コミット変更は引き継がれないため、必要な変更が基準コミットに含まれることを確認する。比較基準はコミットのハッシュで固定し、旧版で後日修正しても基準結果を再現できるようにする。
3. 現行ディレクトリを`slide-studio-old`へ移す。メインの作業ツリーか追加worktreeかを確認して移動方法を選び、既存worktreeがある場合は参照を修復する。移動後、`slide-studio-old`のチェックアウト先を比較用ブランチ`legacy/python`へ切り替える。ブランチを作るだけでmainを開いたままにしない。未コミット変更を保持したうえで、`git worktree list`と各作業ツリーの`git status`で確認する。
4. 記録したコミットから`migration/electron`を作り、空いた`slide-studio`へworktreeを追加する。両方で本計画を参照できる状態にする。
5. エディター・ターミナル・エージェントの作業場所を開き直す。旧パスを含む仮想環境の起動スクリプト等は確認し、必要な環境だけ再作成する。既存の実データで移行試験をしない。
6. 旧版と移行版は、別のテスト用保管フォルダ・設定・ポートで動作比較する。移行版に利用者の通常の保管フォルダを自動で選ばせない。

メインのGit管理情報が`slide-studio-old/.git`にある構成では、新しいworktreeもそこを参照する。比較が終わっても`slide-studio-old`をディレクトリごと削除しない。将来整理する場合は、先にGit管理情報とworktreeの配置を整理する。

並列実装用のworktreeは、この2つとは別に担当ごとに作る。既存コードを単純コピーして独立したリポジトリを作る方式は採らない。今回の計画追記ではディレクトリ移動を実行せず、実装開始時のM0で行う。

### 3.2 移行版の内部構成

予定する配置は次のとおり。

```text
slide-studio/
  apps/
    desktop/                 Electron main・preload・起動処理
    server/                  localhost HTTP API・SSE・CLI入口
  packages/
    core/                    原稿・保存・ビルド・履歴等の共通処理
    ai/                      AI CLI・会話・権限・ログイン
    renderer/                Electronによる検査・画像・PDF
    web/                     共通HTML・素のJS・CSS・strings.js
    runtime/                 配布HTML用JS・Lua・テンプレート
  scripts/                   検証・配布・並列作業の補助
  resources/                 取得手順・配布メタデータ。巨大バイナリはGit管理しない
  tests/                     契約テスト・fixture・E2E・移行比較
  docs/                      設計判断・移植対応表・本計画
  .github/workflows/         CI・OS別ビルド・Release
  slide_studio/              移行期間だけ残すPython参照実装
  package.json
  pnpm-workspace.yaml
  pnpm-lock.yaml
```

バックエンドはTypeScript、既存画面はES moduleを維持する。React等へのUI全面移行は含めない。パッケージ管理はpnpmとし、npmコマンドは使わない。Node・pnpm・Electron・PandocはM0で対応版を確認し、バージョンとlockfileを固定する。開発時だけNode・pnpmを必要とし、利用者のPCには導入を求めない。

ルートAGENTS.mdは索引のまま維持する。従来のPython専用規約はCONTRIBUTING.md側で移行期と移行後を区別する。atomic write、UI日本語の一元管理、変更箇所だけの原稿書き戻しは継承する。移行期間中もUI文言の管理先は1か所に保つ。

予定する開発コマンドは`pnpm dev:desktop`、`pnpm dev:web`、`pnpm test`、`pnpm typecheck`、`pnpm dist`。これらはこれから実装するコマンドで、現時点では存在しない。

## 4. 共通処理と起動モード

### 4.1 共通処理の境界

coreはElectronのAPIを直接importしない。ファイル操作、プロセス、描画などを明示的なインターフェースとして渡す。HTML生成や原稿操作はUIなしでも実行できるようにする。

最初は既存の相対URLのHTTP API・SSEを維持し、互換テストで置き換える。デスクトップ版とブラウザー版は同じserverとcoreを利用する。フォルダ選択などOS固有操作だけを限定的なpreload経由で呼ぶ。長い変換・AI実行・検査はジョブとして扱い、進捗・キャンセル・失敗を両モードに同じ形式で返す。

### 4.2 起動モード

| モード | 動作 | 描画・書き出し |
|---|---|---|
| デスクトップ | Electronが共通サーバーと編集ウィンドウを起動 | 同梱Chromiumの専用WebContentsを使用 |
| ブラウザー | 同じElectron実行環境をバックグラウンドで起動し、既定ブラウザーでlocalhostを開く | 裏で同じrendererサービスを使用 |
| バッチCLI | 同じ配布物をUIなしのコマンドモードで起動 | HTMLのみなら描画サービスを起動せず、PDF・画像・検査時に起動 |

ブラウザー版も完全な機能を保つため、バックグラウンドではElectronを使う。ここでいう「UIなし」は編集ウィンドウを出さない意味であり、GUIセッションのないLinuxサーバーで動く保証ではない。Linux配布・サーバー用途は初回の完了条件に含めない。

ブラウザー版をNodeだけで動かし、検査のために別Chromiumをダウンロードする構成にはしない。将来別のrendererを選べる境界は残すが、最初の製品ではElectron rendererに揃える。

同一保管フォルダを複数プロセスで同時に書き換えない。書き込みとジョブ管理のロックはホスト1つだけが持ち、CLIクライアントは取得しない。稼働中のホストがある場合、CLIはそこへ検査・相談を依頼し、結果・標準出力・終了コードを呼び出し元へ返す。ホストがない場合だけ単独のコマンドモードを起動する。

AIのサンドボックス内ではlocalhost通信も使えないことがあるため、現行の`ai/bridge.py`と同様に、保管フォルダ内の要求・応答ファイルを介する経路を維持する。依頼ID、許可された操作、キャンセル、タイムアウト、終了時の清掃を共通契約にする。読み取り用検査は原稿の確定スナップショットを入力とし、検査の進行中に編集されても結果の版を識別できるようにする。

WindowsでCLIランチャーの標準出力・終了コードが取れるか、引用符や空白パスが保たれるかをM1で試す。ElectronのRunAsNode利用を前提にせず、採用するランチャー方式とfuse設定の両立を確認する。CLIのためだけにアプリの権限を広げない。

ブラウザー版には終了操作を設け、編集タブ・検査ジョブ・バックグラウンドホストの寿命を区別する。ブラウザー版は既定ブラウザーと裏のElectronを使うため、実行時のブラウザープロセスが1系統になるわけではない。初回の正式検証対象はChrome／Edgeとし、Safari／Firefoxは対応確認が済むまで制約を明示する。

### 4.3 rendererとプロセスの権限

デッキのHTMLや持ち込まれた図は、ユーザーが作った実行可能なコンテンツとして扱う。編集用UIとスライド・外部ページを区別し、Node統合を無効化、contextIsolationとsandboxを有効化する。デッキのiframe・検査用WebContentsには、ファイル操作や任意コマンドを実行できるpreloadを渡さない。

localhostに限定して待ち受け、Origin・Host・入力パス・起動ごとの接続資格を検査する。管理APIの資格は管理UIだけが保持する起動ごとのトークンとし、状態変更要求には専用ヘッダーを必須にする。ポート違いではCookieが分離されないため、Cookieだけの認証に依存しない。デッキから管理APIへのCORSを許可しない。初回のブラウザー接続とSSEの認証方法も契約に含め、トークンを素材URL・ログ・外部リンクへ漏らさない。

管理UIと素材配信のオリジン／セッションを分離する。M0で親画面とデッキiframeのDOM直接操作を洗い出し、必要箇所をM2でpostMessageの型付き契約へ置き換える。送受信元、メッセージ種類、対象ブロックを検証し、任意JS・任意API呼び出しを受け付けない。M1の直接編集試験は、この分離を有効にした状態でも行う。

外部リンクとAIログインは既定ブラウザーで開き、Electron内部への任意ナビゲーションを許さない。デッキ・素材パスの範囲チェックはcore側でも行う。

必要なAPIだけをIPCに公開し、IPC引数・呼び出し元を検証する。Electronの[セキュリティ指針](https://www.electronjs.org/docs/latest/tutorial/security)を確認して実装する。

## 5. Chromium統一と出力品質

現在のPlaywrightの役割を、ElectronのWebContents操作へ段階的に移す。`executeJavaScript`等による状態操作、JSエラー収集、素材の読込失敗検出、通信制限、画像取得、`printToPDF`、PDF結合までを置き換える。[ElectronのPDF API](https://www.electronjs.org/docs/latest/api/web-contents#contentsprinttopdfoptions)を使用する。

- 起動は必要時に行い、ジョブをキューで制御する。初期の重い描画ジョブは1本に制限し、実測後に並列数を調整する。
- 編集用WebContentsを検査のためにページ送りしない。検査・出力には独立したWebContentsを使う。
- 非表示時のタイマー抑制、バックグラウンド描画、フォント・画像・iframe・数式の準備完了を明示的に扱う。固定秒数待ちに依存しない。
- 既存の`deckReady`、`deck.go`、`pdfSteps`、`layout-check.js`を活用する。CSS・JSを別形式へ作り直さない。
- PDFは16:9、指定step数、文字の検索・選択、日本語、SVG、数式、リンクを検証する。全ページの画像化で代替しない。
- PDF結合ライブラリはpdf-lib等を候補として、日本語・メタデータ・ページサイズ・ライセンスをM1で確認して固定する。
- HTML解析はparse5系、YAMLはyaml等を候補とし、BeautifulSoup等との出力差を既存fixtureで判定する。採用ライブラリを先に決めて差を許容する順序にはしない。
- Pandocは既存のLuaフィルターを維持し、常駐プロトコルと単発フォールバックを移植する。終了時には子孫プロセスまで回収する。
- Chromiumを使うテストは開発依存に置く。最終製品にテスト用Playwrightブラウザーを混入させない。

同じChromiumでも、MacとWindowsでフォント・描画結果が完全に一致する保証はない。M1で標準テーマと日本語フォントの同梱方針を決め、OS別の基準画像で検証する。フォントを同梱する場合は再配布条件も確認する。M0のPython比較結果は同梱予定と同じPandoc版で取得し、変換エンジンの版の違いと移植による差を区別する。

## 6. 保存場所と既存データ

| 種類 | 保存場所・方針 |
|---|---|
| 原稿・メモ・画像・文献・テーマ・履歴 | 利用者が選んだ保管フォルダ。現在の`decks/`、`topics/`、`themes/`、`.slide-studio/`を維持 |
| アプリ本体・Pandoc・標準資産 | アプリの読取専用リソース |
| 最近の保管場所・設定 | OS標準のアプリデータ領域 |
| AI CLI・キャッシュ・更新途中のファイル | ユーザー単位のアプリデータ／キャッシュ領域 |
| AIの認証情報 | 各公式CLIの管理に任せる。アプリはトークンを収集・複製しない |

初回画面は「新しくフォルダを作る／既存のフォルダを使う」。候補は`~/Slides`で固定しない。保存場所の切り替え・最近の場所・消失時の再選択を維持する。デスクトップはOSの選択ダイアログ、ブラウザーは既存の選択UIを基本とする。

旧`~/.config/slide-studio/location.json`は初回移行で読み、元を残して新形式へ記録する。`--root`と`SLIDE_STUDIO_HOME`の優先順位を継承する。旧AI設定の移行はCLI自身が扱える保存場所の継続利用を優先し、認証トークンをアプリでコピーしない。

atomic writeは同一ディレクトリの一時ファイルから置換する共通関数へ移す。Windowsのファイルロック、読取専用フォルダ、Unicode・空白を含むパス、ドライブ境界、シンボリックリンクを試す。保存失敗時に元ファイルを壊さない。

データ形式を変える場合はバージョンを付け、コピー上で移行試験と復元試験を行う。アプリの更新・再インストール・アンインストールで利用者の保管フォルダを削除しない。初回リリースではクラウド同期機能を新設しない。

## 7. AI機能とCLI互換

アプリ利用者向けのAI機能と、今回の実装に使う開発エージェントは別の設定で管理する。アプリの標準AIをDeepSeekへ変更する計画ではない。

既存のCodex、Claude Code、Antigravityのプロバイダー境界・会話再開・モデル選択・各役割・キャンセル・スナップショット・相談CLIを移植する。WindowsではUnixのkillpgに相当する終了処理を別実装し、起動した子孫だけを終了する。AIのサンドボックスはCLIごとのOS対応を確認し、非対応を理由に無制限実行へ切り替えない。M0で「CLI×OS×役割」の機能表を作り、各項目を「編集可」「会話のみ」「非対応」に分類する。分類はCLIの実際の制約と一致させ、会話のみでも禁止したツールが実行できないことを確認する。UIはこの表に対応させ、制約が残る場合はWindows版全機能対応とは扱わない。

AIが呼ぶ`slide-studio check`・`consult`・`audit`等には、同梱CLIランチャーと実行環境を渡す。Windowsの実行形式・引用符、MacのGUI起動時PATHでも動かす。システム全体のPATH変更は必須にしない。

CLIの取得・更新は公式配布元、バージョン固定、公開ハッシュ検証、起動確認、前版保持を継承する。macOSの署名後にアプリバンドル内部を書き換えない。

Claude Codeは未改変の公式バイナリを利用し、本人の契約で公式フローから認証する。認証方法を制限しない条件、利用の仲介・再販の禁止、提供者側の規約同意を公開前に確認する。現行の`--claudeai`固定を見直し、APIキー等の方法を妨げないか検証する。規約適合をTauri／Electronの選択だけで判断しない。[公式条件](https://code.claude.com/docs/en/legal-and-compliance)

## 8. アプリなしでの再ビルド

既存の保管フォルダにはPythonコンパイラーと`build.py`があるため、この機能を黙って削除しない。

新方式では、同じアプリの展開用アーカイブとコマンドモードを可搬コンパイラーとして提供する。別のコンパイラー実装・別バージョン系列は作らず、アプリと同じビルド・署名・core・Pandocを使う。インストーラーなしでHTML／PDFを生成できるようにし、利用者にPython・uvを要求しない。

保管フォルダにはコンパイラーの版・入手先・使い方を記録し、大きなElectronバイナリを発表フォルダごとに複製しない。元の`build.py`や利用者が編集したREADMEは上書きしない。既存のPython方式は移行前のフォルダで利用可能な旧方式として説明し、新方式への切り替えを明示する。

保管フォルダに形式バージョンと対応コンパイラーの範囲を記録する。未対応の新形式は書き換えず、必要な版と入手先を表示する。旧Python版の最終タグとソース起動手順を残し、初回のElectron配布対象外となるLinuxについても移行文書に記載する。

保存フォルダ、可搬コンパイラー、必要資産を別PCへコピーし、ネット接続なしで再ビルドできることを検証する。「フォルダだけで再ビルド」という旧説明は、新しく必要なコンパイラーの準備を含む説明へ更新する。

## 10. 並列コーディングとレビュー

### 10.1 使用モデル

2026-11-12、手元のOpenCode v2.2.7のモデルAPIと利用者の選択画面で次を確認した。DeepSeekへの実際の呼び出しと、Freeと1017の性能同一性は未検証。性能が同一であることを前提に検証を省略しない。

| 役割 | 呼出元 | モデル指定 |
|---|---|---|
| 実装・テスト修正の第一選択 | OpenCode | `opencode/deepseek-v4.1-flash-free` |
| Freeが利用不能な場合の実装 | OpenCode | `deepseek/deepseek-flash`（表示名：DeepSeek V4.1 Flash 1017） |
| 行き詰まり・設計相談・レビュー | Claude Code CLI | `claude-opus-5-5`、`--effort high` |

`deepseek-flash`は接続先のモデルIDであり、1017という文字列を含まない。実装開始時にもカタログの表示名・モデルIDを確認し、別モデルへ更新されていたら記録して扱いを決める。[OpenCodeのモデル選択](https://opencode.ai/docs/models/)、[Claudeのモデル指定](https://support.claude.com/en/articles/11940350-claude-code-model-configuration)を参照する。

### 10.2 並列単位とファイル所有

契約と共通型を統合担当が先に固定する。とくに原稿の位置・ブロックID・描画要素の対応と、編集後の対応更新を共通契約に含める。最大3本の実装タスクを別worktree・別ブランチ・別セッションで動かす。重いE2E・Electronビルドは同時実行を抑え、モデルの並列数とテストの並列数を分けて管理する。

| 担当 | 所有する領域 | 並列開始条件 |
|---|---|---|
| A 原稿・保存 | core/source、edit、workspace、history、対応テスト | 共通型・atomic write契約の確定 |
| B 描画・書き出し | renderer、Pandoc、bundle、PDF、対応テスト | RenderJob契約とfixtureの確定 |
| C AI・起動／配布 | 初期はai・process、後半はdesktop・配布・サイトを別タスク化 | provider契約、後半はバイナリ名とRelease形式の確定 |
| 統合担当 | 共通型、lockfile、API契約、マージ、移植表 | 各担当の成果物を確認して順に統合 |
| Opusレビュー | 差分・失敗再現・設計判断の読取と指摘 | 基盤確定時、各タスク完了時、各マイルストーン完了時 |

統合担当は本計画を実行する主担当エージェントとし、コーディングは指定のDeepSeekへ割り当て、設計・統合判断の確認にOpusを使う。共通契約、Aの原稿基盤、Bの描画、CのAI／起動の順を基本に、契約テストを通したコミットを順次取り込む。

同じファイルを複数の実装担当に割り当てない。依存追加は統合担当へ申請してlockfileをまとめて更新する。共通契約を変える場合は影響先へ通知し、古い契約で進む担当を止めて同期する。サイトは別リポジトリのため、別worktreeで作業する。

各依頼には目的、対象ファイル、編集禁止範囲、入出力契約、fixture、完了条件、実行するテストを記載する。成果物にはcommit／差分、テスト結果、未解決事項、変更した契約を添える。作業が止まっても同じ依頼を重複起動しない。

### 10.3 Free優先と切り替え

M0で`scripts/agents/`に担当起動・状態記録・再開用資料の生成を行う補助ツールを設計し、M2までに実装する。worktree、ブランチ、セッションID、使用モデル、対象ファイル、終了状態、検証結果をタスク単位で記録する。共有のモデル利用状態と並列上限を管理し、以下の切り替え条件をコードで判定する。プロバイダーのエラー形式が不明な場合は、エラーを保存して分類し、文字列の推測だけで有料へ切り替えない。

- 通常はFreeで開始し、タスクが難しいことやテスト失敗だけを理由に有料1017へ切り替えない。難しい問題はOpusへ相談する。
- 429等の一時制限はRetry-Afterを尊重し、並列数を下げる。共有の状態で制限を管理し、全担当が同時に再試行しない。
- 明確な無料枠終了・モデル提供停止は切り替え対象。5xxやタイムアウトは段階的に最大3回再試行し、継続する場合に切り替える。認証設定の誤りは先に修正する。
- 1017の利用はユーザーから指定済み。切り替える際は理由・対象タスク・開始時刻を記録し、使用量・取得できる料金情報を集計する。無制限の自動再試行は行わない。
- Freeが復旧したら新規タスクから戻す。進行中の1017の作業は途中で重複実行しない。
- モデルを切り替える前に作業差分・失敗ログを保存し、先行プロセスの終了を確認する。再開機能が使えなければ、同じworktreeで引継ぎ資料を渡して新規セッションを作る。
- 明示モデルが使えない場合のOpenCode既定モデルへの意図しない切り替えを防ぐ。指定モデルと実際のモデルが一致するかログで確認する。

### 10.4 Opusへの相談と確認

同じ問題に2回修正を試して改善しない場合、原稿保全・権限・PDF品質・更新方式の設計判断が必要な場合、実装担当が原因を説明できない場合はOpusへ相談する。再現手順、最小fixture、差分、失敗ログ、試した対策を渡す。

レビューでは、未編集原文の保持、機能の欠落、Windows差分、IPC／ファイルの境界、プロセス終了、PDF品質、テストの妥当性を確認する。レビュー担当には通常書き込み権限を渡さず、実装担当が指摘を修正する。Opusに修正を担当させる必要がある場合は、対象ファイルの所有権を一時移して競合を防ぐ。

呼び出し例は以下。実装開始時のCLI helpに合わせて確認する。プロンプトは実装担当がシェル文字列に埋め込まず、ファイル・標準入力またはargvで渡す。

```sh
# 作業ディレクトリは担当ごとのworktree。2〜3件を独立プロセスで実行する。
opencode run --model opencode/deepseek-v4.1-flash-free --format json --file TASK.md 'TASK.mdの担当範囲を実装し、指定テストまで実行する'

# Freeが利用不能になった場合。同じタスクの先行プロセスを停止してから実行する。
opencode run --model deepseek/deepseek-flash --format json --file HANDOFF.md '引継ぎ内容と現在の差分を確認して続行する'

# 提供資料だけを読ませるレビュー。--tools ""でコード変更やコマンド実行をさせない。
claude -p --model claude-opus-5-5 --effort high --tools "" --output-format json < REVIEW.md
```

リポジトリを直接読ませるレビューでは、必要な読取ツールだけを明示的に許可する。`bypassPermissions`や無制限の`--auto`を標準にしない。APIキー・認証トークンをプロンプト、引継ぎ資料、Git、公開CIログへ含めない。今回の開発モデルの設定を製品のAI設定へ混ぜない。

## 11. 検証と性能

Python関数を直接呼ぶ単体テストはTSへ移植する。既存のE2E・fixture・出力比較は可能な限り再利用する。テストをすべて最初から書き直す順序にはしない。

M0でアプリ／テスト起動用ラッパーを用意する。保管フォルダ、設定、移行元データ、Electron userData、キャッシュは担当・試験ごとの一時領域へ向け、実際の保存場所の設定を参照しない。OSの既定パスを取得する処理は注入可能にし、アプリの子プロセスに必要なAPPDATA・XDG等だけを個別設定する。エージェント本体のHOMEや認証領域は変更しない。テスト用userDataをロック取得前に設定し、HTTPポートは0番のbindで割り当て、実ポートを起動元へ通知する。

OpenCodeの実装担当にはworktreeと専用の一時領域への書き込みだけを許可し、モデル通信・必要な依存取得・承認済みfixture以外の外部送信を制限する。依頼前にFree提供元のデータ取扱条件を確認し、個人の原稿や秘密情報を含めない。実装エージェントのアクセス制約は、その起動方式で有効か試験する。

M0で代表fixtureを固定する。日本語、数式、文献、表、SVG、iframeのアニメーション、複数step、画像、長い発表、テーマ、直接編集、履歴復元を含める。個人の実データは許可なくテスト資産へ追加しない。

| 層 | 確認すること |
|---|---|
| 原稿・保存 | 編集対象以外のバイト差分、改行、引用、Unicode、復元、保存失敗 |
| HTTP／SSE | 既存レスポンス・イベント順序・切断・再接続・キャンセル |
| UI | 日本語IME、選択、貼り付け、Undo、ドラッグ、ショートカット、外部リンク、ダウンロード |
| 描画 | 要素の座標、はみ出し・重なり、欠損素材、JSエラー、背景検査 |
| PDF／HTML | ページ数・サイズ・文字抽出・基準画像、オフライン動作、外部通信なし |
| AI | fake CLIで会話・権限・キャンセル・再開・エラー。実CLI疎通は別ジョブ |
| OS | macOS arm64／x64、Windows x64でインストールと主要操作。Windows ARM64は初回対象外 |
| 配布 | 開発環境なし、ネット切断、更新失敗、空白／日本語パス、アプリ移動、子プロセス終了 |

性能はAI未使用時とAI使用時を分け、画面だけでなく子プロセス全体を測る。デスクトップ版とブラウザー版も分ける。ブラウザー版は測定用の独立したブラウザープロファイルを使い、そのブラウザーのプロセスも合計に含める。

- 冷起動／再起動から編集可能になるまでの時間。
- 編集・背景検査中の全プロセス合計メモリ、CPU、アイドル復帰。
- HTML／PDF出力時間と最大メモリ。
- ダウンロードサイズ、展開後サイズ、AI取得後の追加サイズ。
- 繰り返し開閉・検査後のメモリ増加、残留プロセス。

同じPC・同じfixture・同じ操作で各5回以上測り、中央値と最大値を記録する。基準に対して起動・主要処理の中央値または合計メモリが10%以上悪化した場合は原因調査とOpusレビューの対象とし、自動で許容しない。この10%は初期の調査基準で、性能保証ではない。M0で取得した基準値とM1の結果から、公開前に満たす数値を決定して記録する。

## 12. ビルド・Release・更新

初回の正式対象はmacOS Apple Silicon／Intel、Windows x64。OS別のCIでビルドし、同梱Pandoc・AI取得先・署名・パスを確認する。対応OSの下限は、選定したElectronとAI CLIが対応する範囲でM0に固定する。

署名・公証・Windows署名の要否、既存アカウント／証明書の有無、費用が生じる準備をM0で整理する。M1で最小アプリの配布・更新試作を行い、署名が揃っている場合は署名付き更新まで通す。署名不足で未実行の部分は明示し、M6に初めて発見する状態にしない。未署名版は内部試験と手動更新に限定し、正式公開の代替として黙って採用しない。

パッケージ化はelectron-builder＋electron-updaterを第一候補とし、M1で現行安定版の対応を確認する。macOSはDMGと更新用ZIP、WindowsはNSISインストーラーを基本とする。選んだツールの更新形式に合わせてメタデータとハッシュを生成する。形式の違うautoUpdaterを混用しない。

ReleaseのバージョンはGit tag・package・表示・可搬コンパイラー・サイトの配布情報で揃える。成果物にOS・CPUを含む安定した命名規則を設け、SHA-256、変更点、対応OS、ライセンス一覧を添える。

CIはPRの型検査・関連テスト、OS別統合、tagからの署名付きビルド、draft Release作成を分ける。秘密情報は公開ソースと分離する。全資産の揃ったdraftを検証してから公開し、公開後にサイトのダウンロード先を更新する。署名・公証・Windows署名に必要なアカウント／証明書がない場合は、その不足を記録し、未署名の内部試験版と正式配布版を区別する。

アプリには更新確認・取得・再起動のUIを用意する。編集中や書き出し中に無条件で再起動しない。途中失敗時は現行版で起動可能に保ち、公開済みの前版インストーラーを保持する。データ移行が入る更新はバックアップと復元手順を付ける。

[Electronの更新機構](https://www.electronjs.org/docs/latest/tutorial/updates)と採用する[electron-builder](https://www.electron.build/)の安定版ドキュメントを基に実装する。
